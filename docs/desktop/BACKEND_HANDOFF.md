# Lab Station backend handoff

## Device provisioning integration (backend commit 9b6dab0)

Source and `docs/acceptance/DEVICE_PROVISIONING_CONTRACT.md` were inspected.
The actual backend implements operator management at
`POST/GET /api/v1/education-admin/organizations/:organizationId/devices`,
`GET .../:deviceId`, and `POST .../:deviceId/{suspend,resume,revoke,rotate-credential}`.
It implements device calls at `POST /api/v1/devices/enroll/start`,
`POST .../enroll/complete`, `POST .../auth/challenge`, `POST .../auth/token`,
`GET .../me`, and `POST .../me/heartbeat`. These routes are gated by
`DEVICE_PROVISIONING_ENABLED` (default off); operator lifecycle routes require
School Admin `education.devices.manage` or System Admin `org.manage`.

Desktop now stores the Ed25519 private key using OS encrypted storage, signs
the backend enrollment/auth challenges, keeps the short-lived device token in
memory, checks `GET /devices/me`, and sends heartbeat. It never creates AWS IoT
certificates. Admin suspension/revocation/rotation remain operator LMS actions;
the student Desktop has no admin user session and intentionally does not call
them. Device session failures stop provisioning verification rather than being
reported as active. Provisioning UI accepts the administrator-issued one-time
code and reports backend-confirmed status.

## Desktop-generated simulation telemetry contract gap

The Education API exposes `POST /api/v1/me/attempts/:attemptId/digital-twin/viewer-scope`;
the actual route verifies the in-progress attempt, student membership, classroom
allocation and robot entitlement. The Twin service exposes
`POST /internal/simulation-telemetry` for trusted server publishers. It is
internal server-to-server and must not be called by Desktop with a student or
device token. The inspected backend has no Desktop-authenticated route that
accepts frames generated by the local MuJoCo simulation, binds them to the
active attempt/assignment/robot, and forwards them to the authorized Twin
session. The exact contract gap is a route such as
`POST /api/v1/me/attempts/:attemptId/simulation-telemetry` (or a server-managed
experiment route) with frame schema validation and server-side signed publish.

For a real Desktop → broker → authorized Twin flow, provide a contract such as
`POST /api/v1/me/attempts/:attemptId/simulation-telemetry` (or a server-managed
experiment route). The API must validate the student session and active attempt,
check classroom/assignment/robot entitlements and frame schema, enforce rate and
size limits, and perform the server-side signed publish to the Twin. Return a
correlated ACK/result and define expiry, revocation, reconnect and stale-frame
semantics. Until then, Desktop may display local MuJoCo frames and transport
messages to an explicitly configured local broker, but must not present those
frames as a backend-authorized Twin session.

## AWS IoT requirements

Provide a non-production AWS IoT endpoint for integration testing, a per-device
certificate policy scoped to that device and assigned lab, topic names and
payload schemas, command TTL and deduplication behavior, ACK/result correlation,
telemetry retention, certificate rotation and revocation process, and an
offline/reconnect policy. The desktop must not contain shared AWS credentials.
MQTT may carry authorized lab commands and results but must never carry servo
setpoints or other real-time control traffic.

## Current state

No AWS IoT credential/policy provider is connected. Backend device-key
enrollment is integrated, but it is not an AWS certificate or MQTT credential.
The inspected backend lacks the student-authenticated MuJoCo telemetry bridge.
